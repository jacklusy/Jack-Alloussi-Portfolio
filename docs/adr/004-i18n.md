# ADR-004: Four-language i18n with a structure/text content split

## Status

Accepted.

## Context

The portfolio needed full multilingual support (German default, English, French, Arabic with RTL) without compromising the existing typed-content architecture (ADR-001) or the home page's performance-tuned motion.

## Decision

- **Routing**: `next-intl`, locale-prefixed URLs (`/de`, `/en`, `/fr`, `/ar`), `localePrefix: 'always'`. German is the default for new visitors; the browser's `Accept-Language` is deliberately ignored (`localeDetection: false`) — only an explicit choice via the language switcher (stored in the `NEXT_LOCALE` cookie) changes it on a later visit. See `src/proxy.ts`.
- **Content split**: every content entity is stored as language-neutral **structure** (TypeScript, `src/content/*.ts`) plus per-language **text** (JSON, `src/i18n/content/<locale>/*.json`). `src/content/index.ts` merges the two per request and re-validates with the existing Zod schemas, extended with `*StructureSchema` / `*TextSchema` pairs. This keeps ADR-001's guarantee (invalid content fails the build) across all four languages, and keeps proper nouns (NestJS, PostgreSQL, Stockwell, …) defined once instead of duplicated per language.
- **UI strings**: a separate `src/i18n/messages/<locale>.json` catalogue, outside the content split, since chrome text (nav, buttons, errors, a11y labels) has no "structure" half.
- **Translation workflow**: English extracted first as the source of truth for keys; German/French/Arabic written to match (12 project case studies translated by parallel sub-agents against a shared glossary, `docs/i18n-glossary.md`, then checked for structural parity).
- **RTL**: Tailwind logical properties (`ps-`/`pe-`/`ms-`/`me-`/`start-`/`end-`) replace physical ones across the UI; a `useDirection`/`useInlineSign` hook flips the `Reveal` motion primitive's offsets; `:lang(ar)` CSS swaps in an Arabic font and disables letter-tracking/uppercase (which break Arabic letter joining).
- **Guard rail**: `tests/unit/i18n.test.ts` asserts every locale has identical keys, array lengths and ICU placeholders to English, with no empty strings, for both the message catalogue and the content JSON.

## Consequences

- A client component must never import `@/content` (the merge layer) directly — it would pull every language's prose into the bundle. Server components call it; data needed client-side is passed down as props (see `Header`, `Footer`).
- Adding a fifth language means: one row in `src/i18n/config.ts`, one `messages/<locale>.json`, one `content/<locale>/**` tree. The structure files do not change.
- Translations here are model-authored. A native-speaker review is recommended, German in particular (the CV stays English-only and is labelled as such in every language).
